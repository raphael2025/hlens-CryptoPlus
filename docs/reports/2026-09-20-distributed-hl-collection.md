# Hyperliquid 采集要不要改成分布式多出口（设计裁决，2026-09-20）

> 本文只做设计裁决，不改任何既有文档、不改任何代码。上限放宽到 200 行（`AGENTS §11` 的例外由本次派单给出）。
> 数字标签沿用 `04` 的四种：`官方` / `实测` / `估算` / `未验证`。`实测` 来自 `docs/reports/2026-09-20-m1b-hub-inventory.md`，其 HL 数一律附 `样本不足`。
> 涉及旧系统的地方只写「生产出口」「某境外节点」，不写机器名、IP、路径、token。

## 0. 结论

**(c) 不做分布式多出口采集 —— M1 不做，M5 也不做。** 一句话理由：**分布式买到的是「更多 HL 权重」，而没有任何确认功能需要更多权重**；真正坏掉的那件事（邻居的自配额 1200 > 整条出口天花板 1080）分布式解决不了，它只能让我们躲开，而躲开有一个便宜两个数量级的办法：**请 raphael 把旧采集器在该出口的自配额压到 ≤ 900**。

进程数不变：**4 个常驻容器 + 2 个宿主定时器**，`§6` 一行不动。

若 raphael 拒绝压配额，升级路径是 `§6.1` 否决备选 ③「换出口」（`估算` 半天，+1 个常驻转发组件），**仍然不是分布式采集**。理由见 §3 第 4 行与 §7。

## 2. 一、要不要做、什么时候做

### 2.1 分布式到底多买到什么

只有两样：**① 额外的 HL 权重预算**（5 个不花我们钱的出口，`估算` 合计可用 5 × 1080 = 5400/分）；**② 与邻居的隔离**（我们的 HL 请求不再与那台越线的采集器共用一个被计数的 IP）。

两样都要对着 `§17` 的判据过一遍：**没有确认功能消费它就不做。**

- **对 ①**：M1 需要 44，M5 需要 ≤ 124，天花板是 1080。**没有任何 `02-FEATURES.md` 的确认功能需要超过 124/分的 HL 权重**；F11 的两年费率回补走 opportunistic 车道，`§6.1` 已裁决「跑 5.5 天是设计内的，不是故障」。所以 5400 的产能没有消费者 → 按 `§17` 删除。
- **对 ②**：这是真需求，因为邻居确实会把整条出口打到 1147。**但隔离不等于分布式。** 隔离的最小实现是「换一条出口」，一个转发组件就够；分布式额外附带任务队列、租约、配额服务、5 个远端常驻进程和一份跨机时钟假设 —— 那些部件买到的全是 ①，而 ① 没有消费者。

**一句话：分布式 = 「换出口」+ 一堆为无人消费的产能而付的钱。**

### 2.2 更便宜的那条路：压配额

M1-B 的报告说「压它的配额是唯一真正的修法」。**我核对了它在代码上成不成立，结论是成立，但比报告写的多一个坑：**

- 旧采集器的配额模块有一个 AIMD 自调器，每 5 秒跑一次：撞 429 砍到 75%；连续 10 分钟平均用量 ≥ 当前预算的 90% 就 +60；硬顶由一个环境变量给、默认 1200。
- **因此「手动把那个出口的每分钟预算改小」不成立** —— 只要它继续贴顶，自调器每 10 分钟加 60，一小时内爬回去。这一条是对 M1-B 报告那句话的补正。
- **真正压得住的只有两种改法**：
  - **(甲) 把硬顶环境变量全局降到 900。** 自调器里有一条「硬顶调小了，存量预算也要收回来」的分支，所以这一改立刻生效且不会被爬回去。`估算` 0.5 小时，0 行代码。**代价**：它是全局的，5 个不花我们预算的出口一起降 25%，旧采集器一轮由约 2.9 小时变成约 3.9 小时（`估算`，按预算线性折算；它实际卡在单次调用耗时而不是配额时，影响会更小）。
  - **(乙) 给配额表加一个「每出口硬顶」列，只压生产出口那一行。** `估算` 1–2 小时 + 一个测试。**代价**：改了一个即将退役的生产系统的代码，正是 `§6.1` 否决备选 ① 的那条理由。
- **压到 900 之后**：我们可用 = 1080 − 900 = **180/分**。M1 的 44 占 24%，M5 的 124 占 69%，还剩 56 的退避余量。**M1 与 M5 一起解决。**

**压配额与分布式的对比，一句话**：压配额把「邻居会越线」这件事**消除**，分布式只是让我们**躲开**它 —— 而邻居越线本身是 raphael 自己那套生产采集在挨 429，躲开它对他没有任何好处。**解决优于规避。**

### 2.3 为什么不是 (a) M1 就上 / (b) M5 再上

- **(a) M1 就上**：M1 的 44 在 127 里占 35%，`§6.1` 的算式装得下。为一个装得下的负载建一套分布式采集，会把 `01 §5.2` 的 M1（~160 h）撑大 `估算` 60–100 h。而 **M1 是整个产品里唯一有真实日历压力的里程碑**：`01 §5.2` 第 1 条写着 M6 的词典与记分板需要 M1 之后至少 3 个月自采历史，**没采的分钟永远补不回来**。任何拖慢 M1 上线的东西都是在花 M6 的日历时间买 M1 的产能，而那产能没人消费。
- **(b) M5 再上**：M5 的 +80 有三条更便宜的出路（压配额 / 退役 / 把 200 这个数重新推导一遍，见 §2.4），全都排在分布式前面。**而且 M5 上分布式有一个循环矛盾**：它要复用的 7 节点属于那套「必须先退役、M5 才能开 HL 现采」的系统（`§15`）。见 §4。

### 2.4 M5 的 +80 是不是一个真数字（这条本身可能就把问题解掉）

`§6.1` 写的是「200 地址 × `clearinghouseState` = +80/分」。但 `§15` / 决定 C3 给的需求是「**按账户价值取 TOP N，N 取到样本 n ≥ 100 为止**」。**200 不是从 n ≥ 100 推出来的，它是一个被填进算式的数。** 如果 TOP 100 就够 n ≥ 100，追加是 **+40/分**，`44 + 40 = 84 < 127` —— **连压配额都不需要，现在的账面份额就装得下。**

反方向的证据也要说：旧系统实测全库只有约 14.7% 的地址真有永续仓位（`实测`；但那是全库口径，**对 TOP N 不成立，标 `未验证`**）。若 TOP N 的有仓率也偏低，N 就得大于 100。

**裁决**：**M5 开 HL 现采之前，必须先用导入的排行榜与持仓历史离线算一次「TOP N 里有永续仓位的比例」，把 N 定下来。** 这是一次零权重的离线查询，`估算` 2 小时。**在这个数出来之前，任何为 +80 买基础设施的论证都是在给一个没验算过的数字付钱。**

### 2.5 触发条件：什么情况下本裁决作废

写死三条，任一成立就回来重开本文：

1. raphael 明确拒绝压配额，**且**拒绝换出口 —— 那时 M5 的 HL 现采只能门控于退役，`§15` 已经是这个结论，仍然不需要分布式。
2. 出现一条确认功能，其 HL 稳态需求 > 180/分（压配额后的份额）。当前 `F1`–`F31` 里没有。
3. 压配额后的三档实测使 `我们的稳态 + 邻居的 max > 1080`。**这一条最可能成立**，因为现在只有一档 29 分钟的样本。

## 4. 三、复用还是自建（这是个真矛盾，讲清楚）

**复用旧系统的 7 节点与它的配额模块**：省掉全部硬件与大半实现，但让**生产分钟链路依赖一套「必须先退役、M5 才能开」的系统**（`§15`）。这是一个闭环：M5 门控于退役 → 我们为 M5 建的分布式依赖那套系统 → 它退役我们就断 → 于是它不能退役 → M5 永远开不了。**复用这条路在逻辑上走不通，不是「代价大」，是「自相矛盾」。**

**自建一套**：不继承矛盾，但 5 个出口要么花钱（见上，吃光成本上限），要么复用已有机器 —— 已有的只有新疆 NAS 与机房备用服务器，而 `§17` 明写「备用服务器不跑生产链路、不持有生产密钥」。**把它拉进分钟链路要推翻那条裁决**，而它当前承担的是「生产挂了之后的静态兜底」；让兜底与被兜底的东西同生共死，是把备份写进主链路。

**结论：两条都不通。** 顺带一提，这也解释了为什么「换出口」是更好的退路 —— 它只需要**一个**转发点，而机房那台备用服务器做**纯转发**（不落库、不持生产密钥、挂了只影响 HL 一条道）并不违反上面那条裁决的本意。**其所在地区对 HL 是否可达 `未验证`**（HL 拒绝部分地区），要先探一次。

## 5. 四、如果真要做：唯一可接受的形状（三个子问题的答案）

**本节是条件性的**，结论是不做；写在这里是为了让将来重开这个问题的人不必从头推。

### 5.1 数据怎么回来：经 hub 的 HTTP，绝不直连 Postgres

四条理由，任一单独成立：① 直连让 `market_1m` 有 N 个写方，撞 `§4` 与 §3 第 4 行的跨机时钟问题；② 数据库要对 tailnet 开端口，`§1`「不开任何公网端口」的简化优势吐回去一半；③ 库凭据要发到 5 台远端机器，撞 `AGENTS §3`；④ worker 保持哑的、纯标准库，才可能不成为第二套要维护的软件 —— 旧系统正是这么做的（哑 worker 发请求、回传 body，hub 解析落库），且它的 v2 设计文档把这一点列为**刻意不改**的前提。

**代价要说清**：hub 从此是分钟链路的**必需在线组件**，它挂了远端也白采。

### 5.2 配额：我核对了派单里那句话，**它不对**

派单说「`SpendAuthority` 是结构化 Protocol，远程实现天然满足、适配器一行不改」。读完 `adapters/admission.py` 与 `adapters/hyperliquid/adapter.py`：

- **对的那一半**：`SpendAuthority` 确实是结构化 `Protocol`，在 priority 上逆变、在 grant 上不变；适配器拿到的 `AnyAdmission` 是 `Admission[Any, Any]`，**grant 对适配器完全不透明**（`acquire` 拿到、原样交回 `settle`）。所以一个远程实现在**类型上**确实满足，适配器的类型标注一行不用改。
- **错的那一半**：`acquire` / `settle` / `release` 全是**同步 `def`**，而适配器在 `async def` 里直接 `grant = admission.acquire(cost)`（`adapters/hyperliquid/adapter.py:316`）。**远程实现意味着在事件循环里做一次阻塞 RPC**，每个请求多一跳 —— 这正是 `§6.1` 否决备选 ① 的原话「每次请求多一次数据库往返，为一个会消失的问题引进一条永久的热路径」。改成 `async` 就要动 Protocol，而 Protocol 一动，**两个适配器的每个方法都要跟着改**，这正是接缝 ② 存在要防的代价。
- **旧系统早就撞过这堵墙并给了答案**：它的分工是「**hub 分配份额，worker 本地执行**」，理由写在它的配额模块注释里：hub 的记账天然滞后（发请求 → 回传 → 才落库），拿滞后数据做实时闸门必然有竞态。
- **所以正确的远程形状不需要远程 `SpendAuthority`**：hub 周期性下发一个**更小的天花板**，worker 侧仍跑本地 `RateLimitLedger`。落到我们的代码上，这是「在配置加载处注入一个动态 ceiling」，**不是**一个新的 authority 实现。这条纠正本身就削掉了分布式的大半「天然契合」论据。

**租约语义（`Grant` 要补什么）**：我们的 `Grant` 没有到期时间，本地用不着（同进程）。跨机就必须有，且**必须朝保守方向失效**：份额 TTL ≤ 60 秒，过期后 worker 的本地上限**掉到一个配置的地板，绝不保留上一次的值**。旧系统的 worker 恰恰是保留旧值（下发失败就沿用上一次），在网络分区下会与 hub 重新分配给存活节点的份额叠加、双倍超发 —— 那正是它自己记在注释里的「V3 的坑」，只是换了一个触发路径。**份额必须闭着失效，任务租约才能像旧系统那样靠「租约到期就抢回来重派」兜底。**

### 5.3 失败面与 `§13`

要新增三行：**worker 掉线**（远端静默 → 该出口的道停摆）、**网络分区**（hub 与 worker 互相看不见，双方都以为自己该继续）、**hub 挂掉**（远端全白采）。第二行最贵：它要求上面那条「份额闭着失效」，而**闭着失效的代价是「hub 抖一下，全部远端一起降到地板」** —— 一个把局部故障放大成全局故障的设计。`§13` 现在没有任何一行长这样。

## 6. 五、数据模型要改什么（这决定 `M1-C` 现在能不能派）

**按结论 (c)：一个字都不用改，`M1-C` 现在就能派。**

- **`ingest_gap.cause` 十值闭枚举**：不加值。「worker 掉线 / 租约过期」在 (c) 下不存在。**若将来做**，只加**一个**值 `remote_worker_down`，写方 collector，**且不计入口径 A 的排除集** —— 它是我们自己的组件在坏，和 `unknown` 同一条道理（`§5` 已写明排除集不能变成逃生口）；`lease_expired` 不单独立值，它是同一件事的子类，多一个值只会让排障时多一次分类犹豫。
- **`market_1m` 的写方与覆盖语义**：(c) 下写方仍是 1，`(venue, symbol, ts)` 主键与三条列组 upsert 守卫**全部不动**。若将来做，只允许 §5.1 的形状（哑 worker + 单一写方），**因为跨机直写会静默破坏 `obs_ts_*` 守卫**（§3 第 4 行）；这一条必须写进 `§5`，否则将来有人会把「worker 直写」当成显然的优化。
- **`M1-C` 仍必须回答的那个老问题**（与本文无关，但它才是 `M1-C` 的真阻塞）：`oi_usd` 在入库边界算还是在 `compute` 层算，以及快慢两道先到后到时的取值语义（`§5` 2026-09-20 裁决）。**本文不解这题。**

## 8. 七、要 raphael 拍板的（按重要性排）

1. **压不压旧采集器在生产出口的配额**（压到 900 → 我们得 180/分，M1 与 M5 一起解决）。并选 **(甲) 全局降硬顶**（0 代码，5 个免费出口一起降 25%，一轮 `估算` 由 2.9 h 变 3.9 h）还是 **(乙) 加一个每出口硬顶**（`估算` 1–2 h，改了一套即将退役的系统）。
2. **压完之后要不要重测**：现在只有一档 29 分钟样本（`样本不足`）。建议压完后再取一次三档 p95 **与 max**，否则 M5 的 69% 占用是建立在一个下界上的。
3. **M5 的 N 到底是多少**（§2.4）：先离线算「TOP N 里有永续仓位的比例」，再决定是 +40 还是 +80。**这件事排在任何基础设施之前。**
4. **若第 1 条被拒**：是否启用 `§6.1` 备选 ③ 换出口，以及是否允许机房那台备用服务器做纯转发（会碰到 `§17`「备用服务器不跑生产链路」的边界，要一次明确裁决）。
5. **旧采集器的退役时间** —— `§18 第 4 条` 仍然空着，它决定上面每一条的时间价值。

## 9. 未验证清单
