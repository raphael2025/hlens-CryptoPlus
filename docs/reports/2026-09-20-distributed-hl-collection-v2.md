## 1. 第一原则：只分布该分布的东西

把 HL 的活按「能不能分」和「在不在分钟链路上」摊开，答案就写在表里：

| 工作 | 节奏 / 权重 | 能分布吗 | 在分钟链路上吗 | 裁决 |
|---|---|---|---|---|
| 快道 `metaAndAssetCtxs` | 每 30 s 一次，W=20 → 40/分（`估算`） | **不能**：它是一次全市场调用，拆不开；只能「搬家」或「复制」 | **是**（F2 ≤ 60 s） | **永远留在生产主机**。搬家等于把 M1 验收押在 tailnet 上；复制等于花两份权重买同一份数据 |
| 元数据 `meta` | 每 8 h，W=20 | 不能 | 否 | 留在主机 |
| **M5 钱包 fan-out** `clearinghouseState` | 每 5 min 一轮 N 个地址，W=2/个 | **能**，天然按地址切 | 否（`01 §4.5` 现采持仓类 ≤ **5 分钟**） | **分布**。这是第一个真需求 |
| **F11 费率回补** `fundingHistory` | opportunistic，合计 157,680 权重（`估算`） | **能**，按币与时间段切 | 否（`§6.1`：跑 5.5 天是设计内的） | **分布**。这是第二个真需求，也是最安全的试验场 |

**这张表就是本设计与 hlens 最大的不同**：hlens 把每一件事都塞进任务队列（连排行榜探测都是一个 task），于是它的控制面成了所有采集的必经之路。我们**只把 fan-out 与 opportunistic 放上去，分钟链路一步都不经过远端**。三个直接后果：

1. worker 全挂 → **一条分钟缺口都不产生**（§6 会再证一次）；
2. `§4` 与 `§5` 不用改（§5 一节）；
3. M1 验收不受影响（§7 一节）。

## 2. 一、租约：热路径不做 RPC

### 2.1 一次往返 = 续租 + 交结果 + 领单

**worker 拉，hub 不推。** 每 `POLL_SEC`（默认 15 s，`估算`；只服务 ≤5 分钟与 opportunistic 两档，余量充足）worker 发**一个** POST：

```
上行  { worker_id, egress_hash, lease_epoch, results:[ {order_id, status, body, ms, hdrs} ] }
下行  { lease: {epoch, bucket, ceiling_per_min, min_spacing_ms, ttl_ms, banned_until_ms},
        orders:[ {order_id, host_key, path, body, est_weight, deadline_ms} ] }
```

hlens 用三个端点（心跳 / 派活 / 回传）；这里是一个。**理由不是省代码，是省状态机**：续租、交货、领单三件事在同一次往返里原子发生，就不存在「租约续上了但结果没交」这类中间态，凌晨排障时一条日志能看全。

**这个端点住在哪**：`collector` 容器里的**又一个 asyncio 任务**，监听 tailnet 地址，不开公网端口。**所以 `§6`「4 个常驻容器 + 2 个宿主定时器，没有第五个容器」保住了**，`§6`「`collector` 内部不拆进程」也保住了——它不是拆进程，是同一进程里多一个 asyncio 任务，和现有的健康、导出、通知任务同类。
**一处知情的手工活**：`§14` 裁决「API 形态与 Web 框架：不选」。为了不推翻它，这一个端点用 `asyncio.start_server` 手写（`估算` ≈ 80 行，单路由、token 鉴权、JSON 进出），**不引入 FastAPI**。**触发线**：将来需要第二个端点时，这条裁决重开。

### 2.2 租约的真正作用：它是授权的有效期，不是预算的分配单位

这是本设计与 hlens 分野的地方，要说透。

hlens 的份额是**分配**用的：同一出口可能跑 N 个 worker，hub 把 1200 除以 N 发下去。**我们没有这个问题**——**一个出口只放一个我们的 worker**（§3 的 fail-closed 规则会强制这一点）。于是「分配」这件事退化成一个静态配置值。

**那租约还剩什么用？一件，而且是 hlens 恰好没有的那件：让 worker 在失去联系时停下来。** hlens 的 worker 在拿不到下发时**沿用上一次的份额**，并有一个静态默认值兜底；网络分区时它会带着旧份额继续花，而 hub 那边已经按「活着的 worker 数」重新分配——这正是它自己写在注释里的「V3 的坑」换了个触发路径。

**我们的规则：没有未过期的租约，就一个权重都不许花。** 租约是授权，不是预算；失联即停，**绝不沿用旧值**。代价是「hub 抖一下，远端停一会儿」——而远端跑的全是 ≤5 分钟与 opportunistic 的活，停一会儿只产生**可见的陈旧**（`as_of` 置灰），不产生静默超发。**拿「可见的慢」换「静默的错」，在单人运维下永远划算。**

### 2.3 粒度 · 时长 · 续租 · 过期 · 纪元

| 项 | 定死的值 | 为什么 |
|---|---|---|
| **粒度** | 一张租约 = 一个 `(worker, 出口, 桶)`。桶沿用 `venue:bucket`（如 `hyperliquid:info_weight`） | 按任务发租约就回到「每请求一次 RPC」；按出口发才对得上交易所的记账维度 |
| **内容** | `ceiling_per_min` · `min_spacing_ms` · `ttl_ms` · `epoch` · `banned_until_ms` | 两个限速器要两个旋钮：权重限速器调 `ceiling`，连接速率限速器调 `min_spacing`（§2.5） |
| **时长** | `ttl = 120 s`，续租每 15 s 一次 | 给 7 次续租机会再过期，容得下 3 次连续失败 + 一次重启。hlens 用 120 s 活性判定 + 30 s 心跳（`实测`其配置），同一量级，沿用这条经验 |
| **过期口径** | **worker 用自己的单调时钟从收到那一刻起算 `ttl_ms`**，hub 下发的是**时长不是绝对时刻** | 前一份文档的发现：跨机墙钟不可比。发绝对时刻，NTP 偏差就能凭空延长租约；发时长，偏差只影响谁先超时，方向是保守的 |
| **hub 侧判活** | hub 认为租约在 `issued_at + ttl + skew_margin`（`估算` 5 s）之前仍然有效 | 两边都留余量，且 hub 的余量**更长**，保证「hub 认为死了」严格晚于「worker 认为自己死了」 |
| **纪元（fencing）** | 每个 `(出口, 桶)` 一个单调递增 `epoch`。**hub 在上一张租约按它自己的口径过期之前，绝不为同一个出口签发新租约**；worker 上行必须带 `lease_epoch`，对不上的结果照收（数据不丢）但**不予续租** | 这是防「hub 以为 worker 死了、发给替补，而旧 worker 还活着」的唯一手段。一个出口同时只有一张有效租约 = 同一个出口不可能有两份预算 |
| **过期后果** | 本地上限**直接归零**，不是降级；恢复要重新领租约 | 见 §2.2 |

### 2.4 租约期内撞 429 / 418 —— 手上有额度，交易所说不行

**总原则一句话：租约是上限，不是额度；本地随时可以更低，永远不许更高。**

| 情形 | worker 立刻做 | 回传后 hub 做 |
|---|---|---|
| **429，body 是 JSON `null`**（权重限速器，`04 §3` 的判据） | 本地 AIMD 砍到 75%；opportunistic 冻结 1 小时（与 `§6.1` 单机版同一套规矩） | 把**该出口该桶**的 `ceiling` 按 AIMD 下调（§4），下一张租约按新值签发 |
| **429，body 是 HTML**（连接速率限速器） | **不是退权重**，是拉长 `min_spacing_ms`。worker 严格单槽（并发已经是 1），所以唯一能降的就是发送间隔 | 下调该出口的 `min_spacing`，写 `ops_event` |
| **418 / 被封** | 立即停该出口该 venue 的全部发送，**主动交还租约**（上行带 `surrender`），读 `Retry-After` 记进 `banned_until` | 该出口标 `banned_until`，**期间不签发任何租约**；写 `ingest_gap(cause=ip_ban)` + F4 私聊 |
| **续租拿不到响应** | 继续花完**当前租约**剩余的额度直到 TTL 到期，然后归零 | 到期后自动可以另签（epoch+1） |

**一条 `§6.1` 的连带规则需要 raphael 点头修改**：原文「任何一次 HL 429 都必须发一条 F4 私聊」，理由是共用 IP 上「另一个消费者可能也在挨打」。**在只有我们一个消费者的专用出口上这个理由不成立**，照搬会造出一个每次正常 AIMD 都响的呼机。**建议**：共用出口的 429 → 私聊（不变）；专用出口的 429 → `ops_event` + 状态页计数，**1 小时内 ≥ 3 次**才升级为私聊。

### 2.5 否决的备选

| 备选 | 为什么不 |
|---|---|
| 远程 `SpendAuthority`（每次 `acquire` 一次 RPC） | `acquire` 是同步 `def`，适配器在 `async def` 里直接调（`adapters/binance/adapter.py:275`、`adapters/hyperliquid/adapter.py:316`）。远程化 = 在事件循环里阻塞；改 `async` 就要动 Protocol，两个适配器每个方法跟着改，正是接缝 ② 要防的代价 |
| 共享一张 Postgres 令牌桶表 | `§6.1` 否决备选 ① 的原话：每次请求多一次数据库往返。跨机之后还多一段 WAN |
| hub 实时闸门（hub 记账、worker 每次问） | hlens 自己的注释写明为什么不行：hub 的记账天然滞后（发请求 → 回传 → 才落库），拿滞后数据做实时闸门必然有竞态 |
| 不发租约，静态配置每个出口的上限 | **这其实是 90% 的形状**，租约只比它多一条「失联即停」。但那一条是 hlens 的坑的正面解，值一个 TTL 字段 |

### 2.6 为什么「适配器一行不改」是真的（机制）

适配器声明的 `CallCost(bucket="hyperliquid:info_weight")` **与出口无关**，因为适配器根本不知道这次会从哪个出口发——这是对的。出口维度落在**调用方的接线**里：

- `collector` 持有 **N 个 `Admission`**，每个绑一个出口的账本；要从出口 B 发，就用 `admission_b` 调适配器。适配器签名本来就是 `async def mark_prices(self, *, admission: AnyAdmission, ...)`，**传哪一个由调用方决定**。
- 这正是 `admission.py` 文档串里那句话的自然延伸：「the one line that knows both is in the collector's wiring」。
- **两级记账**：host 侧每个远端出口一份**影子账本**（防止多签单），worker 侧一份 ~30 行的滚动 60 秒窗口（**权威**）。两者在回传时对账，差值上状态页——`Grant`、`SpendAuthority`、`_BUCKET_RE`、`Priority` **全部零改动**。

## 3. 二、出口账本认外来消费者

**公式与单机版同一套，只多一维**：

```
出口 E 上某桶的天花板 = 官方上限 × 使用比例 − Σ(该出口上已申报的外来消费者)
```

`config/egress-consumers.yaml` 现在是「消费者 → 桶 → 预留额」；分布式版本在最外层加一维 `egress`：

```yaml
egress:
  prod:                                  # 生产出口（我们的主机 + 旧采集器的一个 worker + 开发机）
    label: "生产出口"
    expected_hash: "<盐哈希，值只在机器 .env 里>"
    consumers:
      - {name: hub_legacy, bucket: hyperliquid:info_weight, reserved_per_min: 953,
         source: measured, note: "样本不足；见 M1-B", checked_by: "...", assertion: "..."}
  node_a:                                # 某境外节点
    label: "出口 A"
    expected_hash: "<...>"
    consumers:
      - {name: hub_legacy_worker, bucket: hyperliquid:info_weight,
         reserved_per_min: <未测得>, source: unverified}
```

**四条规则，每条都对着 hlens 的一个缺陷**：

1. **未申报的出口，天花板是 0，不是官方值。** hlens 的 `ensure_budget()` 给任何第一次出现的出口 IP 按默认值建预算（默认 1200）——**一台新机器接进来就自动获得满额授权**，这正是共用出口上自配 1200 的来源。我们反过来：**配置里没写的出口，一个权重都不给**。
2. **外来消费者的预留额必须带 `source` 标签，`0` 必须带 `assertion` 与 `checked_by`。** 这条单机版已经有（`Reservation.is_assertion_of_zero` + `§6.1` 回收流程第 ③ 步），原样继承到每个出口。
3. **谁维护**：raphael，手工，每个 `(出口, 外来消费者, 桶)` 一行；每次改动在 `ops_event` 留一行。**代理不得自行填数**——它只能报告「未测得」。
4. **preflight 在每个节点上怎么校验**（每次启动 + 每小时）：① 算本机出口哈希，与它被配成的那个 `egress.expected_hash` 比对，**不符即拒绝启动**（否则它会用 A 的额度在 B 上花钱，或两个节点悄悄落到同一个出口上双花）；② 打印该出口的扣减表（官方 × 比例 − Σ 申报 = 我们的上限），与单机版同一张表、同一个格式；③ 断言该出口的 `Σ 申报 + 我们的上限 = 天花板`，不等即拒绝加载——**这条加载器已经有了**（`config.py:889`），只是现在按出口各跑一次；④ 出口哈希在运行中改变（动态 IP / 线路切换）→ 立即交还租约并停止发送，写 `ingest_gap(cause=egress_change)`，该值已在十值枚举里。

> **必做的前置实测**：M1-B 只读到了**生产出口**那一份账本，**其余 5 个出口的占用「未测得」**。按规则 1，它们现在的天花板是 0，**在测出来之前一台都不能用**。读法与 M1-B 相同（读旧系统控制面自己的账本，零交易所调用），`估算` 1 h。

## 4. 三、自调器：每出口每桶一份硬顶，clamp 的对象是申报值

hlens 的硬顶是一个**全局环境变量**（默认 1200），`AUTO_STEP=60` / `AUTO_UP_EVERY_SEC=600` 会把手改的预算一小时内爬回去——压一个出口就得连累其余 5 个。我们的版本：

| 规则 | 值 |
|---|---|
| 状态粒度 | 每 `(出口, 桶)` 一份，不是每出口一份。HL 权重桶挨打不该牵连零权重端点 |
| **上界** | **该出口该桶的申报天花板**（§3 的公式算出来的那个数），**不是环境变量，也没有环境变量可以覆盖** |
| 上调 | 四条同时成立才 +step：① 近 10 分钟平均用量 ≥ 当前的 90%；② 自上次变更以来无 429；③ 距上次变更 ≥ 10 分钟；④ `min(step, 申报天花板 − 当前)` |
| 下调 | 权重 429 → ×0.75；下界是该桶的快道地板（远端不跑快道，故为 0） |
| 抬高申报天花板 | **只能改配置 + 重跑 preflight + 写 `ops_event`**，即一个有人签字的决定。与 `§6.1` 对 `reserved` 的纪律一致 |
| 429 计数窗口 | 只数**上次调整之后**的。hlens 这里踩过坑并修好了（固定「近 5 分钟」会把同一次事故重复计，实测 1200→900→675→600 十几秒崩到地板），**这条经验直接沿用** |

## 5. 四、写方归属：选 (i)，并且 `§4` `§5` 一字不改

**选 (i)：worker 不写库，hub 是唯一写方。** worker 连 Postgres 的地址都不知道。

**代价（正面说）**：hub 成为必经之路与单点。**但这个代价的大小取决于让什么过它**，而 §1 的表已经把分钟链路挡在外面：过 hub 的只有 M5 的每 5 分钟一轮和 opportunistic 回补。量级：N=200 时每分钟 40 条结果、每条 `估算` 2–8 KB → **峰值 ≈ 0.3 MB/分**，落库是批量 `copy()` 进临时表再 upsert（`§3` 已定）。hub 挂了的后果是「大户面陈旧并置灰」，不是「分钟缺口」。**这是可以接受的单点，因为它的下游没有一条 ≤60 秒的承诺。**

**为什么不是 (ii) 按 `venue + symbol` 分片**：不是哲学问题，是**这两个工作量根本没有 symbol 维度可分**——HL 快道是**一次全市场调用**（分不开，且不分布），M5 的 fan-out 按**地址**切、写的是 `hl_position` / `hl_fill`（主键里没有可用来分片的 symbol）。**(ii) 在这里无处可用。** 若将来真要用，`§4` 那句话的准确措辞是：「每张表只有一个写**模块**；同一模块多进程写同一张表时，必须有一个由**主键**决定的静态分片函数，任何两个进程的分片不相交，且分片函数随迁移版本化」。**仍然更差**：它把「这一行是谁写坏的」从一个静态事实变成一个「当时哪个分片拥有它」的运行时问题。

**`§5` 的三条 upsert 要怎么改：一条都不改。** 逐条核：

- **快道 / 慢道两条**：写方仍然只有生产主机上的 `collector`，远端永远不写它们 → 前一份文档指出的「跨机时钟让 `obs_ts_* >` 守卫退化成『时钟最快的赢』」**不可能发生**。
- **回补那条**：远端 opportunistic 的产出经 hub 落库，走的是**回补语句**（`backfilled=true`，守卫 `WHERE market_1m.backfilled AND excluded.grid_s <= market_1m.grid_s`）。这条守卫**不看 `obs_ts_*`、只比网格粒度**，天然幂等、与顺序无关，多少个远端节点供数都不影响结果。
- **M5 的表**：`hl_position` / `hl_fill` / `hl_leaderboard` 在 M5 新建，写方是主机上的 `whale` / `import` 模块。

## 6. 五、失败面与 `ingest_gap.cause`

**先把最重要的一条证出来**：M1/M2 的分钟链路（快道 + 慢道）完全在生产主机上，**远端全体下线不产生任何 `market_1m` 缺口**。所以下面三行故障，没有一行会动 M1 的验收口径。

`§13` 建议新增三行（若本文被采纳，由 raphael 回填）：

| 最先坏的 | 怎么发现 | 数据怎么诚实记录 |
|---|---|---|
| **远端 worker 掉线 / 节点重启** | 该出口的租约续不上，hub 侧 TTL 到期；状态页每出口一行变红 | M2：无缺口（回补可续跑，`backfill_cursor`）。M5：`ingest_gap(venue=hyperliquid, metric=hl_position, cause=remote_worker_down)`，大户面按 `01 §4.5` 置灰 |
| **网络分区**（hub 与 worker 互相看不见） | 同上；且 worker 侧自己知道续租失败 | 两边都朝保守方向：worker 花完当前租约即停，hub 等 `ttl + skew` 后才允许换人（epoch+1）。**双花在结构上不可能** |
| **hub / 租约端点不可达**（容器重启、`compose pull`） | 远端连续续租失败；主机侧 `collector_run` 照常 | 分钟链路不受影响。恢复后远端自动重新领租约；期间的 M5 缺口按上面第一行记 |

**枚举要不要加值：加一个，`remote_worker_down`，而且是在 M5 的迁移里加，不在 `M1-C`。**

- **为什么现有十个装不下**：`venue_error` 的语义是「该源返回非 2xx 或 WS 静默」，而它同时驱动 `source_health` → F5 的按源置灰。**远端节点掉线时把它记成 `venue_error`，站上会对用户说「Hyperliquid 落后了」——而 Hyperliquid 好得很，是我们的盒子没了。这是拿错误信息骗用户，比少一个枚举值严重得多。** `egress_down` 的写方与判据是 health 对**本机**出网的探测；`power_loss` / `host_restart` 由生产主机自己的 `pg_controldata` 与 uptime 判定，对远端一无所知。`unknown` 在算术上装得下，但 `§5` 故意把它排除在口径 A 的排除集外正是为了让它难看、没人愿意往里塞——把一类**可精确判定**的故障常态化塞进 `unknown`，等于把那条设计意图废掉。
- **写方**：`collector`（hub 侧的租约管理器，它是唯一知道租约到期的地方）。
- **是否计入口径 A 的排除集**：**否**。远端节点是我们自己的组件，它坏了就该算我们头上，和 `unknown` 同一条道理。
- **明确不加的两个**：`lease_expired`——租约过期的**原因**就是 worker 或链路没了，两个名字会把同一次事故拆成两行，让「缺口可解释率」更难审；`shard_unclaimed`——选了 (i) 就没有分片。
- **代价**：给一个十值 `CHECK` 加第十一个值 = 一次 `DROP CONSTRAINT` + `ADD CONSTRAINT ... NOT VALID` + `VALIDATE`，在分区表上逐分区做，`估算` 分钟级，一次迁移。**所以 `M1-C` 今天就能派，按十值封闭枚举建表，不必为分布式预留。**

## 7. 六、复用边界：复用机器，自建软件

**软件不复用。** 复用 `hub/quota.py` 与它的任务队列，等于让生产链路依赖一套「必须先退役、M5 才能开」的系统（`§15`），前一份文档已证这是个闭环矛盾。本文不重复。

**机器复用——但要先问清楚。** M1-B 实测那 5 个独立出口节点现在就在线，成本对我们是 0。**但它们是为旧采集器存在的**：旧采集器退役时，那几台是留着还是退租？**`未验证`，raphael 必答。** 若退租，本设计的出口就没了，机器成本从 0 变成 `估算` 4–6 美元/台/月。

**最小可行 worker（自建，`估算` ≈ 200 行，纯标准库 + 一个 HTTP 客户端）**：

1. **它不懂任何交易所。** 它收到的是**发送单**（`{host_key, path, body, est_weight}`），host_key 指向 `config/venues.yaml` 里的地址（`AGENTS §2.3`：主机名不进代码）。加一个所，worker **零改动**——**权重表继续住在适配器里，接缝 ② 保住**。
2. **它不懂归一化。** 原样回传 `status + body + 耗时 + 响应头`，由主机上的适配器归一成契约对象。**接缝 ① 一步都没跨出主机。**
3. **它只会三件事**：滚动 60 秒记账（~30 行）、按 `min_spacing_ms` 间隔发送、把 429 的 body 原样带回（`04 §3`：HL 的 429 body 类型是判断哪个限速器的唯一证据）。
4. **严格单槽 + 批量领单。** hlens 实测过：一次往返只给一个任务时，某境外节点 98% 的周期花在等控制面（约 2.5 s 等 / 43 ms 调用）。**这条教训直接拿来用**——领单批量化、执行仍单槽。
5. **它不持有任何生产密钥**：一个 worker token（只能换租约与交结果）、一个 tailnet 身份，没有库凭据、没有备份密钥。

## 8. 七、分期，以及 M1 验收的正面回答

**M1：不上，零分布式代码。** 三条理由：

1. **没有消费者。** M1 的 HL 稳态 44/分，账面份额 127/分（`实测`，`样本不足`），占 35%。
2. **正面回答「会不会让 14 天 ≥ 95% 更难过」——如果放进 M1，会。** 不是因为它会造成分钟缺口（§1 的设计保证它不会），而是因为**它在 M1 里没有活干，却要在验收窗口里被安装、被排障、被误报**。验收测的是「两源分钟级采集连续 14 天绿」，往那个窗口里塞一个没有产出的常驻件，只可能减分。
3. **而它天然不必进 M1**：`§16` 规定 **M2 在 M1 连续 14 天稳定之后才开始**。把第一个分布式工作量（F11/M2-1 的回补）放在 M2，它在物理上就进不了 M1 的验收窗口。

| 阶段 | 上什么 | 为什么是这里 |
|---|---|---|
| **M1** | 无 | 见上。`M1-C` 按十值枚举建表，照常派 |
| **M2** | 租约端点 + 1 个远端节点，只跑 **opportunistic 回补** | 第一个真工作量，且**失败零代价**（可续跑、不在分钟链路、`§6.1` 明说跑几天是设计内的）。用它把租约、fencing、AIMD、失联即停这四件事在低风险负载上跑熟 |
| **M5** | 扩到 2–3 个节点，跑钱包 fan-out | 这是硬需求，也是**把 M5 从「门控于退役」解锁**的那条路 |

## 10. 九、M5 的规模：N=100 与 N=200 两档

`§6.1` 的 `+80/分` 出自「200 地址」，而需求写的是「TOP N 取到样本 n ≥ 100 为止」（决定 C3）——**200 从没被推导过**。**本设计对 N 不敏感**：fan-out 的工作单元是「一个地址」，每个出口能扛多少地址由该出口的申报天花板决定，N 是配置值不是架构值。两档都给：

| 档 | 调用 | 权重 | 加 40% 重试余量后需要的出口余量 | 落地形状 |
|---|---|---|---|---|
| **N=100** | 20 次/分（每 5 分钟一轮，W=2） | **40/分** | **≈ 56/分** | 一个出口即可；极端情况下**连共用出口都装得下**（44 + 40 = 84 < 127），分布式只是把它挪走以免挨邻居的 429 |
| **N=200** | 40 次/分 | **80/分** | **≈ 112/分** | 一个出口（若该出口申报余量 ≥ 112），或两个出口各 40 |

**前置**：N 本身仍由一次零权重的离线核算决定（用导入的排行榜与持仓历史算「TOP N 里有永续仓位的比例」，`估算` 2 h）。**不要为一个没推导过的数字定出口数量。**

## 11. 十、要 raphael 拍板 / 必测清单
